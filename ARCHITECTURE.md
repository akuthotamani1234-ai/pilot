# Blow AI — Architecture Guardrails

Read this file **before** adding or moving files. It protects the codebase during human and assistant-assisted
("vibe coding") changes. Product behavior rules (safety, secrets, verdicts) remain as defined in
`project-docs/03_RULES.md`, `CONTRIBUTING.md`, and `backend/README.md`.

## 1. System shape

Blow AI is a **local QA product** (primary target: Windows) with:

| Layer | Location | Responsibility |
| --- | --- | --- |
| Web UI | `frontend/` | Studio HTML/CSS/JS only — no business verdicts |
| HTTP API / jobs | `backend/server.py`, `backend/mcp_*.py` | Start runs, stream progress, serve reports |
| Pipeline | `backend/graph.py`, `backend/agents/` | LangGraph agents; each agent is `state -> partial state` |
| Shared domain | `backend/*.py` (non-agent modules) | Safety, metrics, Android/web runtimes, contracts |
| Generated tests | `runs/<run>/generated_tests/` (gitignored) | Ephemeral Playwright/Appium scripts |
| Docs | `README.md`, `docs/`, `project-docs/` | Operator and contributor truth |

**Rules decide; optional LLM providers only assist.** Verdicts, severities, and defect categories come from code
(`backend/metrics.py`, reporters, gates). Never invent counts.

## 2. Directory rules (where new code goes)

| Kind of change | Put it here | Do **not** put it here |
| --- | --- | --- |
| UI markup / layout / studio controls | `frontend/*.html`, `frontend/*.css`, `frontend/*.js` | `backend/`, `tests/` (except UI tests) |
| HTTP routes / job orchestration | Prefer extending `backend/server.py` carefully; extract helpers into `backend/` modules when a route block grows | New top-level packages |
| Pipeline step / agent | `backend/agents/<step>.py` and wire in `backend/graph.py` + `backend/state.py` | Ad-hoc scripts in repo root |
| Android / Appium domain | `backend/android*.py`, templates in `backend/templates/` | Duplicating locators inside `frontend/` |
| Safety / secrets / URL policy | `backend/safety.py`, `backend/actions.py` | Inline checks scattered in UI |
| Shared types / state keys | `backend/state.py` (`QAState` TypedDict) | Untyped dict keys invented in one agent only |
| Unit / regression tests | `tests/test_*.py` mirroring the module under test | Embedding heavy live network tests without `@pytest.mark.slow` |
| Operator guides | `docs/` or `project-docs/` | Long essays inside source comments |
| Demo contracts / sample APKs metadata | `demo-apps/` (APKs remain gitignored) | Committing binary APKs or real credentials |
| Validation evidence | `deep_validation/**/*.md` (prefer markdown summaries over huge logs) | Committing `.env`, `runs/`, screenshots dumps |

## 3. Coding constraints

1. **File size:** Prefer **&lt; 400 lines** for new modules; **&lt; 250 lines** for new UI JS files. Existing oversized
   agents (`discovery.py`, `script_generator.py`, `test_design.py`, `server.py`, `android.py`) may only be split with
   the full offline suite green and a dedicated PR.
2. **Single responsibility:** One module = one job. Do not mix FastAPI routes, Playwright crawling, and report HTML
   in a new file.
3. **UI vs business logic:** `frontend/` must not compute release verdicts or bypass safety. It may display server
   results and collect configuration.
4. **No hardcoded secrets:** Use environment variables / `.env` (see `.env.example`). Never commit `.env`.
5. **No hardcoded magic for product policy:** Prefer named settings in `backend/config.py` over scattershot literals.
6. **DRY:** Reuse `backend/safety.redact`, existing Android helpers, and report builders before adding parallel utilities.
7. **Error handling:** Raise/return explicit domain errors (`AndroidEnvironmentError`, `UrlError`, HTTPException with
   clear messages). Do not swallow exceptions empty-handed.
8. **Naming:** `snake_case` Python, clear JS ids matching existing studio patterns. Match nearby style (ruff + project
   comment voice).
9. **Tests:** Every behavior change needs an offline test unless it is docs-only. Mark live/network/emulator work
   `@pytest.mark.slow`.
10. **Attribution:** Do not add `Co-authored-by` AI tags, "Generated by …", or tool watermarks in source or commits.

## 4. Vibe-coding / assistant workflow (mandatory)

Before generating or editing files, an assistant or developer **must**:

1. Read **this file** (`ARCHITECTURE.md`) and the relevant section of `backend/README.md` / `CONTRIBUTING.md`.
2. Search for an existing helper (`rg`, project search) and **reuse** it before creating a new utility.
3. Place the file in the correct directory from §2.
4. Keep new files within size limits; extract helpers instead of growing giants.
5. Update **`.env.example`** and **`README.md`** (Configure section) when adding environment variables.
6. Update **`requirements.txt` / `constraints.txt`** (and run the suite) when adding dependencies — never leave
   unpinned transitive drift undocumented.
7. Run `ruff check` and the relevant offline `pytest` targets before claiming done.
8. Never weaken irreversible-action blocks, secret redaction, or write-guards to "make the demo pass".
